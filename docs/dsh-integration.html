01

目标与边界

你在实盘和模拟盘里的流程是：指标公式筛出候选，再靠人工看技术面和基本面挑出最终标的。全自动运行时这一步没有人，agent 顶上的就是这一步，其余环节保持原样。

三条硬边界

  • 只能否决和重排。agent 的输入是量化层给出的候选池，输出是对每只票的 BUY WATCH EXCLUDE 三选一和 BUY 内的优先级。它不能加入池子外的票，这样整条漏斗仍然可审计。
  • 允许「今日无标的」。全部排除是合法结论，不为凑数降低标准。这和 zt replay 的口径一致：多数交易日的产出本来就是空的。
  • 每条理由标注能否用代码复现。能复现的理由不进 prompt，进 _collect_vetoes 之类的规则层。agent 只留给真正算不出来的事：主线归属、公告解读、硬伤。

明确不做的事

  • 不喂 K 线截图，不引入视觉模型。看图这件事全部转成数字和文字特征（阶段 1），原因见 1.3。
  • 不让 LLM 算指标。所有数值由 Python 现算，和仓库一贯的「LLM 只负责判断与叙事」原则一致。
  • 评估通过之前，agent 的结论不接管仓位。final_picks 在影子期仍等于量化 picks。
  • Kimi 路径不推倒。它留作兜底，直到 dsh 路径在同一天扫描上达到对等。

口径说明：verdict 的颜色沿用 A 股惯例，红为买入、绿为排除，和西方 UI 相反。前端展示时保持这个约定。

02

现状

现有流水线由 zt scan --save 或看板的「一键扫描」触发，路径如下：活跃市值多空区间做总开关，逐票跑 confirm_buy（可交易性 → MACD 一票否决 → 最近 3 根内的 B1 触发 → MACD 与量能确认），再由 select_final_picks 按主线/行业强度排序取 top N。结果落 buy_decisions 表和 data/daily_scans/*.json。

看板上可以再点「交给 Kimi 复核」，它把 picks 连同用户主线清单和市场状态交给 Kimi Code CLI 的 Swarm，分五个方向查龙虎榜、主线归属、公告、硬伤、横向比较，最后汇总成一篇 markdown。落盘的那次复核是这样的：

项目2026-08-07 那次复核
扫描规模4999 只扫描，135 只 BUY，10 只入选
复核耗时约 50 分钟
子 agent 完成数4 / 10（降级汇总）
结论分布建议买入 1 · 观察 5 · 排除 4
量化第一名的下场联创光电（确认分 95）被排除：证监会立案、债务逾期、两连跌停后撬板

这次复核证明了「人的那一眼」有价值，也暴露了它现在的形态为什么没法用：

  • 结论是散文，不是数据。「建议买入 / 观察 / 排除」只存在于 markdown 里，没有按票落库，前端只是链接到报告，scan 的 picks 不因它改变。
  • 不可回放。framework_backtest 的文档写明「不接入 kimi」，因为它靠联网搜索，历史日期上必然看到未来。于是没有任何办法回答「这层判断有没有加分」。
  • 慢且不稳定。50 分钟只拿到不到一半的子报告，靠扫描 ~/.kimi-code/sessions 目录来抓结果。
  • 技术面那只眼睛缺席。复核 prompt 明确让 agent「不要重复做技术面打分」，可你的人工终选里技术面是实打实的一环，B1 公式和看图不是一回事。

阶段总览

阶段按依赖排序，每一阶段都有可独立验收的产出。前两个阶段完全不碰 dsh，一两天内就能拿到第一份「agent 有没有用」的数字。

阶段产出依赖完成标准
0 契约verdict 表与 schema、final_picks 接线、候选池无scan JSON 含 agent_pool 与 final_picks；无 agent 时退回量化 picks 的测试通过
1 特征摘要chart_facts.py、zt facts无as-of 测试：追加未来 K 线不改变输出；全部特征有单测
2 离线回放zt replay --agent offline、分组收益报告0、1；任一 OpenAI 兼容模型2024-09 至今跑完一遍，四组 30 日收益与基准并列，两次运行一致率有数
3 dsh 接入runner、MCP 工具、skill、配置模板0；dsh 五项实测在 2026-08-07 那次扫描上复跑：10 只全部有合法 verdict，总耗时可接受，Kimi 路径仍可切回
4 影子与回流每日自动跑、周报、分歧录入、第一条下沉规则3；PIT 快照连续 8 周周报；离线与影子两条证据方向一致后才切换 final_picks
不排队的一件事

PIT 快照任务第一周就上线。它不依赖任何阶段，而消息面和资金面的历史只能靠日历时间积累，早一天多一天数据。做法见 阶段 4。

阶段 0

契约

先把「人的决定」变成一行可以被回测和统计的数据。这一阶段不需要任何模型，全部是表、schema 和接线。

0.1 表

CREATE TABLE IF NOT EXISTS agent_verdicts (
    ts_code        TEXT NOT NULL,
    trade_date     TEXT NOT NULL,          -- 决策日，与 buy_decisions 对齐
    run_id         TEXT NOT NULL,          -- 一次运行一批：daily-YYYYMMDD-n / replay-<tag>
    mode           TEXT NOT NULL,          -- online / offline
    verdict        TEXT NOT NULL,          -- BUY / WATCH / EXCLUDE
    priority       INTEGER DEFAULT 0,      -- BUY 内 1 最高；非 BUY 为 0
    confidence     REAL,                   -- 0-1
    reasons        TEXT,                   -- JSON [{category, text, computable}]
    evidence       TEXT,                   -- JSON [{source, date, url}]
    chart_facts    TEXT,                   -- JSON：当次喂给 agent 的特征快照
    model          TEXT,
    prompt_version TEXT,
    elapsed_ms     INTEGER,
    tokens         INTEGER,
    user_verdict   TEXT DEFAULT '',        -- 阶段 4 回填：你不同意时写你的结论
    created_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (ts_code, trade_date, run_id)
);
CREATE INDEX IF NOT EXISTS idx_agent_verdicts_run ON agent_verdicts(run_id, verdict);

run_id 进主键是为了让离线回放、影子运行、重跑同一天互不覆盖。旧库靠 CREATE TABLE IF NOT EXISTS 补不上新表之外的列，沿用 database.py 里已有的 ALTER 迁移写法。

0.2 agent 的输出格式

agent 的最终回答必须是且仅是一个 JSON 代码块，runner 用 schema 校验。校验不过重试一次并把错误原样喂回；再不过就记 WATCH，理由写「agent 输出无效」并打标，绝不让一条散文混进表里。

{
  "trade_date": "20260807",
  "no_pick": false,
  "verdicts": [
    {
      "ts_code": "600363.SH",
      "verdict": "EXCLUDE",
      "priority": 0,
      "confidence": 0.9,
      "reasons": [
        {"category": "硬伤",   "text": "8/4 公司及实控人被证监会立案；8/5 披露 5.06 亿逾期", "computable": false},
        {"category": "技术面", "text": "D-3、D-2 连续跌停，D-1 撬板反抽，B1 的 J 值是砸出来的", "computable": true}
      ],
      "evidence": [
        {"source": "界面新闻", "date": "2026-08-04", "url": "https://www.jiemian.com/article/14874293.html"}
      ]
    }
  ],
  "notes": ""
}
category 取值
技术面 · 主线 · 资金面 · 消息面 · 硬伤 · 其他
computable
agent 自评这条理由能否用本地数据算出来。为 true 的理由自动进「待下沉规则」队列，见 4.4
evidence
offline 模式必为空；online 模式每条关键结论至少一条，查不到写「未核实」而不是编
ts_code
必须属于本次候选池，池外代码整条丢弃并记警告

0.3 候选池与 final_picks

  • 候选池：select_final_picks 里 BUY 的票按分组强度排序取前 K，默认 20，参数名 agent_pool。只给 top N 的话 agent 没有重排空间；给全部 BUY 又太贵（那天有 135 只）。
  • final_picks：量化 picks 与 agent BUY 的交集，按 agent 的 priority 排。agent 缺席、超时或全部无效时退回量化 picks 并在 warnings 里写明，扫描永远有结果。
  • 回放接线：framework_backtest.Trade 加 agent_verdict 与 agent_priority 两个字段，summarize 支持按 verdict 分组。
  • 看板：每日选股页在 picks 表上加一列 verdict 芯片，颜色按红买绿排。
完成标准
  • schema 校验、幂等落库、池外代码丢弃、无 agent 退回四个行为各有测试。
  • zt scan --save 的 JSON 多出 agent_pool 与 final_picks，其余字段不变。
  • zt replay 在没有 verdict 时结果与现在完全一致（回归）。
阶段 1

K 线特征摘要

这是 agent 在回放里的眼睛。modules/chart_facts.py 只接收截到 D 日的 K 线序列和几个分组统计，输出一个字典和一段紧凑的中文文本。它是纯函数，不读库、不联网，所以天然 point-in-time。

1.2 文本渲染

喂给 agent 的是这样一段话，每行一个维度，数字带单位，不带任何结论词。下面是示意，数字是编的：

【位置】收盘 23.40，处于 250 日区间 92% 分位；距 250 日高点 -6.1%，距 60 日低点 +38.2%
【前期】20 日 +21.3%，60 日 +64.0%；主升自 0612 起，累计 +71%
【均线】MA5>MA10>MA20>MA60 多头排列；收盘高于 BBI 4.1%
【量能】5/20 日均量比 1.6；近 10 根放量 4 天；D-1 缩量阴线
【涨跌停】近 10 根：涨停 2、跌停 2；D-3、D-2 连续跌停，D-1 撬板
【相对】20 日相对「元器件」中位 +9%，相对全市场中位 +17%
【指标】J 9.6 · MACD DIF>0 无背离 · RSI6 18 · ADX 56 高位 · 沙漏 62 · 麒麟：拉升后期
【风险】score_risk 41；近 60 日无停牌；上市 2843 日

1.3 为什么是文本不是图

  • 同一个股票日期对永远得到同一份输入，回放里两次结果的差异只来自模型判断。
  • 每个特征能单测，「位置百分位算对了吗」是可以验证的；视觉模型对一张图的解读没法验证。
  • 本地算，几乎零成本，回放几千个股票日期对才跑得起。
  • 特征是显式的，分歧案例攒起来后能看出哪些组合有用，下沉成规则。图片路线的依据是黑箱，沉不下来。

唯一的代价是特征必须事先枚举，没想到算的东西 agent 永远看不见。处理办法是把它当兜底实验：只有当分歧案例反复暴露「你一眼看到、特征表里没有」的东西，才拿视觉模型做一次 A/B，补上了再写成新特征。

完成标准
  • zt facts 600363.SH --date 20260807 打印上面那样的文本，--json 输出字典。
  • as-of 测试：给序列追加任意未来 K 线，D 日的输出逐字段不变。
  • 每个特征组至少一个合成序列的单测；边界情况（不足 250 根、停牌缺口、新股）有明确的空值约定。
阶段 2

离线回放：技术面那一半的证据

目的只有一个：在接任何 harness 之前，先量出「agent 对量化候选的技术面判断」有没有超额。这一阶段用任意 OpenAI 兼容接口直调即可，现有 llm_providers.OpenAICompatProvider 就够用，dsh 到阶段 3 再上。

2.1 流程

  1. 先跑一遍现有回放估算规模：zt replay --start 20240924 --workers 14 --csv replay.csv，统计多头区间的决策日数和每日 BUY 数，据此定 K 和预算。
  2. zt replay --agent offline --start 20240924 --pool 20：每个门槛通过的决策日，取候选池，逐只生成 chart_facts，调 agent，写入 run_id=replay-<tag>。
  3. 用现有的 _forward 算 30 日结果，按 verdict 分组汇总：量化原选（pick_rank>0）、agent BUY、agent WATCH、agent EXCLUDE，并列同期等权基准。
  4. 抽 10% 的样本重跑一次，记录 verdict 一致率，作为模型判断稳定性的基线。

2.2 匿名候选

离线模式下 agent 看不到代码和名称，只看到 C07 这样的编号、所属分组名、chart_facts 和市场状态。技术面判断不需要身份；给了身份，模型的训练记忆会替它「回忆」这只票后来怎么走，回放就失真了。绝对日期保留，因为大盘状态是人本来就知道的信息。

2.3 怎么算「有用」

比较看什么建议判据
EXCLUDE 组 vs 量化原选ret_stop 均值与胜率EXCLUDE 组显著更差：说明否决有效
agent BUY 组 vs 量化原选相对等权基准的超额不低于原选：说明重排没有伤害
priority 1 到 3 vs 其余 BUY超额越靠前越好：说明排序有信息
两次运行verdict 一致率低于八成先修 prompt 与特征，别看收益

样本不足 200 笔 verdict 时不下结论。活跃市值门槛让多数交易日为空，这一点要有心理准备；从 2024-09-24 起跑就是为了覆盖一轮完整的多空切换。

完成标准
  • runner 的 offline 路径可以注入一个确定性的假 agent，整条回放在没有模型的情况下有测试。
  • 产出一份 data/reports/agent_replay_<tag>.md，含上表四组数字、基准、样本量、一致率。
  • 报告里逐条列出 agent 给出的 computable: true 理由的频次，作为阶段 4 下沉规则的候选。
阶段 3

dsh 接入

把运行器从「起 Kimi CLI 子进程再去翻会话目录」换成「起 dsh headless 拿最终答案」，工具、清单、红线都做成 dsh 插件。Python 一侧只依赖「子进程 + JSON」这一层契约，换 harness 的成本被压到最低。

3.1 已核实的 dsh 事实

  • DeepSeek 官方，MIT，Node.js，「everything is a plugin」，插件用 pnpm 管理：dsh plugin --profile <name> <pnpm args>。
  • 入口模式：dsh --profile headless "job" 跑一个新会话、打印最终答案后退出；dsh --profile sdk 通过 JSON-RPC stdio 常驻；dsh web 是看板；--patch 叠加配置，--dump-config 查看合成后的配置。
  • 供应商：DeepSeek、Anthropic、OpenAI、Bedrock、Vertex、Azure、Codex，外加自定义 OpenAI 兼容端点（api: openai-completions、baseURL、apiKeyEnv、models），配置在 $DSH_HOME/settings.yaml，密钥在 .credentials.yaml。现在的 Kimi K3 可以作为第二个模型接进去做 A/B。
  • 运行时模式有 Standard、Code mode（模型生成 TypeScript 编排工具调用）、Minimal、Creator。
  • 官方标注 developer preview，原话「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」。
  • 本机 Node 24.20 已装，pnpm 未装。

3.2 动手前先实测的五件事

这些在公开文档里没有写清楚，接入前各花半小时确认，结论记到本节：

  1. headless 模式的标准输出里是否只有最终答案，有没有 JSON 或 stream 输出开关；没有就靠 runner 从末尾截取代码块。
  2. 如何为一次运行指定 preset 与工具白名单，--patch 能否按运行切换 offline / online 两套工具集。
  3. MCP 服务在 settings.yaml 里的注册键名和 stdio 启动方式。
  4. 单次运行的步数上限与超时参数在哪里设。
  5. skill 的目录约定与加载方式，能否像 .kimi-code/skills 那样随仓库走。

阶段 4

影子模式与分歧回流

离线回放只能证明技术面那一半。消息面和基本面的价值只能靠向前的影子运行来证明，同时把你的分歧变成 agent 的训练信号。三条回路写的是同一张表、用的是同一套结算函数。

4.1 PIT 快照（不排队）

  • scripts/snapshot_advanced.py 在每日行情同步之后由 systemd timer 触发，对象是当日候选池加自选股，不是全市场，避开东财的连接重置限流。
  • 抓龙虎榜、资金流、北向、涨停池、解禁、机构调研、电报，每行打上 as_of=trade_date，写进高阶数据自己的缓存库，不进主库，理由同 advanced_data.py 的设计说明。
  • 从快照开始日起，advanced_query(as_of) 在 offline 模式也有数据，消息面的回放边界随日历前移。

4.2 影子运行

  • zt scan --save 完成后自动 run_for_scan(mode="online")，写 daily-YYYYMMDD-1；手动重跑递增序号。
  • zt verdict report --weeks 8：按 verdict 分组的 30 日结果、基准、样本量、一致率，与阶段 2 的报告同一格式，输出到 data/reports/。
  • 切换判据：离线回放不少于 300 笔、影子不少于 8 周，且两边都满足 EXCLUDE 组更差、BUY 组超额不低于原选。两条证据方向不一致就继续影子，不切。

4.3 分歧录入

  • zt verdict disagree 20260807 600363.SH --say BUY --note "…"：回填 user_verdict，并用 review_memory.add_case 建一条案例，归因回放随录随算。
  • 周报里加一行 agent 与你的一致率，按 category 拆分。哪一类分歧最多，就先修哪一类的清单或特征。

4.4 规则下沉

  • computable: true 的理由按文本聚类计频，进入「待下沉」清单。第一条候选已经有了：两连跌停后撬板反抽，这是纯 K 线特征，应直接成为 _collect_vetoes 里的一票否决，然后用 zt replay 比较加规则前后的结果。
  • 每下沉一条，agent 的职责就少一块，它的价值也就更容易被单独衡量。这是长期方向：agent 越用越小，规则越用越多。
完成标准
  • 快照任务连续跑满两周无告警；PIT 表里每条记录的 as_of 等于抓取当日。
  • 周报连续 8 周产出；至少一条规则完成下沉并附回放前后对比。
  • 切换 final_picks 的那次提交里附上两份报告。
05

风险与红线

风险处理
dsh 是 developer preview，接口会破坏性变更锁定版本并记录在 deploy/dsh/；Python 只依赖子进程与 JSON；3.2 的五项实测结论写进本文
回放偷看未来工具服务端强制 as_of；offline 不注册联网工具；候选匿名；chart_facts 只吃截到 D 日的序列并有 as-of 测试
模型判断不稳定固定 prompt_version；10% 样本双跑记一致率；一致率不到八成先修 prompt，不看收益
提示注入候选、特征、主线、抓来的网页全部包在数据标签里并声明不可信，沿用 research_service 现有写法
成本与时长失控每票步数与超时上限；整批 15 分钟；先跑 replay 估规模再定 K
SQLite 写锁verdict 批量写；回放期间不跑同步（与现有约定一致）；PIT 快照不进主库
把 Kimi 报告当标准答案它只是另一个 agent 的意见；标准是 30 日收益和你的 user_verdict
过早接管仓位final_picks 切换只在 4.2 的判据满足后进行，并在提交里附报告
